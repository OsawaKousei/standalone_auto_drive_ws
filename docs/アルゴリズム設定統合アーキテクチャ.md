# アルゴリズム設定統合アーキテクチャ

## 1. 目的

本ドキュメントは、以下を同時に満たすための全体構成を定義する。

- 自己位置推定 (`localization`)・経路生成 (`planning`)・経路追従 (`control`)・センサー/物理モデル (`simulation`) の**設定運用を統一**する。
- 実行時にテキストファイルから設定を読み込み、**再コンパイルなしでアルゴリズムとパラメータを切り替え**る。
- 利用側にはインターフェイスで実装差分を隠蔽しつつ、実装内部では**厳密な型チェック/値検証**を行う。
- デフォルト設定関数の利便性を維持しながら、外部ファイル注入を標準化する。

---

## 2. 背景と現状

### 2.1 現状の良い点

- `ILocalizer` / `IPlanner` / `IController` / `ISensorModel` / `IPhysicsModel` が存在し、利用側の抽象化基盤はある。
- `localization` は既に `ekfLocalizerDefaultConfig()` のようなデフォルト設定を持つ。
- `Result<T>` / `Status` によるエラー伝搬が統一されている。

### 2.2 現状の課題

- エンドポイントで具象型を直接生成しており、アルゴリズム差し替え時に分岐と記述が増えやすい。
- 設定の読込・型変換・検証・インスタンス生成が各機能で分散し、同種コードの重複が発生しやすい。
- `map` / `footprint` / `collision` など、インターフェイスを介さない設定項目もあり、全体設定の入口が混在している。

---

## 3. 設計方針

### 3.1 基本方針

1. **設定の入口は1つ**にする（Scenarioファイル）。
2. **共通処理をコアに集約**する（読込・型取得・検証・エラー整形）。
3. **アルゴリズム固有処理はAdapter化**する（decode + validate + create）。
4. 生成結果は必ずインターフェイス（または値オブジェクト）で受ける。

### 3.2 非目標（今回スコープ外）

- `ISensorModel` の戻り値が `LidarScan` 固定である制約の解消（将来課題として扱う）。

---

## 4. 提案アーキテクチャ

## 4.1 レイヤー構成

### A. Config Core（共通基盤）

責務:

- テキスト設定ファイルのロード（TOMLまたはYAML）
- キー探索・型付き取得
- デフォルト値適用とオーバーレイ
- 必須キー/未知キー/型不一致/範囲違反のエラー化

主なコンポーネント案:

- `ConfigDocument` : パース済みツリー
- `ConfigReader` : `getString`, `getDouble`, `getInt`, `getBool`, `getTable`
- `Validation` : `requirePositive`, `requireRange`, `requireEnum` など
- `ConfigError` : `MissingKey`, `TypeMismatch`, `UnknownKey`, `ConstraintViolation`

### B. Domain Adapter（機能別）

責務:

- 各アルゴリズム向けに `ConfigDocument` から強い型のConfigへ変換
- アルゴリズム固有の意味検証

例:

- `decodeEkfLocalizerConfig(...) -> Result<EkfLocalizerConfig>`
- `decodeAStarPlannerConfig(...) -> Result<AStarPlannerConfig>`
- `decodePurePursuitConfig(...) -> Result<PurePursuitConfig>`
- `decodeLidarConfig(...) -> Result<LidarConfig>`
- `decodeUnicycleConfig(...) -> Result<UnicycleConfig>`

### C. Registry + Factory（動的生成）

責務:

- `algorithm` 文字列から decoder/creator を引き当てる
- decode + validate + create を一連で実行
- 成功時にインターフェイス実体を返す

例:

- `createLocalizer(spec, map) -> Result<std::unique_ptr<ILocalizer>>`
- `createPlanner(spec, checker) -> Result<std::unique_ptr<IPlanner>>`
- `createController(spec) -> Result<std::unique_ptr<IController>>`
- `createSensor(spec) -> Result<std::unique_ptr<ISensorModel>>`
- `createPhysics(spec) -> Result<std::unique_ptr<IPhysicsModel>>`

### D. Simulator Endpoint（組み立て層）

責務:

- Scenarioファイルを読み、依存順で全コンポーネントを構成
- 実行ループに必要なオブジェクトを一括初期化

---

## 5. Scenarioファイル仕様（案）

```toml
[scenario]
name = "localization_control_demo"

[map]
yaml_path = "tools/map.yaml"

[robot.footprint]
vertices = [
  [-0.2, -0.1],
  [ 0.3, -0.1],
  [ 0.3,  0.1],
  [-0.2,  0.1]
]

[simulation.runtime]
delta_t = 0.2
max_steps = 250
goal_tolerance = 0.3

[simulation.collision]
max_translation_step = 0.05
max_rotation_step = 0.05

[localization]
algorithm = "ekf"
config_path = "configs/localization/ekf.toml"

[planning]
algorithm = "astar"
config_path = "configs/planning/astar.toml"

[control]
algorithm = "pure_pursuit"
config_path = "configs/control/pure_pursuit.toml"

[sensor]
algorithm = "lidar"
config_path = "configs/sensor/lidar.toml"

[physics]
algorithm = "unicycle"
config_path = "configs/physics/unicycle.toml"
```

### 仕様上のポイント

- `algorithm` は Registry のキー。
- `config_path` 省略時はデフォルト設定関数を適用可能。
- サブ設定は「デフォルト + ファイル上書き」のオーバーレイを許可。

---

## 6. 初期化シーケンス

1. Scenarioファイル読込
2. `map.yaml_path` から `MapData` 生成
3. `robot.footprint` 生成
4. `simulation.collision` から `CollisionChecker` 生成
5. Factoryで `planner` / `localizer` / `controller` / `sensor` / `physics` を生成
6. 初期姿勢・初期共分散・実行パラメータを設定
7. メインループを実行

依存関係:

- `planner` は `CollisionChecker` に依存
- `localizer` は `MapData` に依存
- `sensor` は実行時に `MapData` と `Pose` を受ける
- `physics` は状態とコマンドに依存

---

## 7. バリデーション戦略

### 7.1 2段階検証

- **構造検証**: 必須キー、型、未知キー、列長など
- **意味検証**: 正値制約、範囲、相関制約（例: `free < occupied`）

### 7.2 エラー方針

- 失敗は `Result<T>` / `Status` で返す。
- エラー文面に「セクション + キー + 期待型/制約」を含める。

例:

- `InvalidInput: control.pure_pursuit.lookahead_distance must be > 0`
- `InvalidInput: localization.algorithm "foo" is not registered`

---

## 8. 共通化による重複削減ポイント

- パース処理を `Config Core` に一本化（機能別の独自パーサ実装を避ける）
- enum 変換や数値制約を共通ヘルパ化
- Factory の登録/生成パターンをテンプレート化
- 「default + file overlay」ロジックを共通化

---

## 9. 既存コードへの適用方針

### 9.1 置換対象

- エンドポイント内の具象直生成・直書き設定
- アルゴリズム切り替えに伴う `if/switch` の散在

### 9.2 維持対象

- 既存インターフェイス（`ILocalizer`, `IPlanner`, `IController`, `ISensorModel`, `IPhysicsModel`）
- 既存アルゴリズム実装本体
- 既存のデフォルト設定関数

---

## 10. 段階導入計画

### Phase 1: Config Core導入

- `ConfigDocument`, `ConfigReader`, 共通Validationを追加
- Scenario最小版（map + controlのみ）で起動可能にする

### Phase 2: Localization/Planning/ControlをFactory化

- 各機能の `algorithm + config_path` を解釈し動的生成
- 既存デフォルト設定との互換を確保

### Phase 3: Sensor/Physics/Collision/Footprint統合

- simulation周りもScenario入力へ統一
- エンドポイントの直書きパラメータを削減

### Phase 4: 拡張

- 新規アルゴリズム追加は「decoder + creator登録」のみで対応
- センサー出力型の一般化は別タスクで実施

---

## 11. 期待効果

- 新アルゴリズム追加時の変更範囲を局所化
- 実験・チューニングの高速化（再コンパイル不要）
- 設定由来バグの早期検出（型/値検証の標準化）
- エンドポイントの責務明確化（組み立て専任）

---

## 12. 補足（運用ルール推奨）

- 設定キー命名は `snake_case` で統一
- `algorithm` 値は小文字固定
- 重大設定（速度上限、衝突判定刻み）は必須キー化
- 実験再現用に「読み込んだ最終設定のダンプ」をログ出力
